# getup-css：素の CSS の設計ルール

素の CSS でサイトを組むときのルール。プリプロセッサも、ユーティリティファーストのフレームワークも使わない。

優先順は `@layer` と記述順で管理し、詳細度を低く揃える。ねらいは、ブラウザ上で値を変えながらデザインを詰めていける（インブラウザデザイン）状態を保つこと。

## この Skill の使い方

- CSS を書く・直す前に、このファイルを読む。
- プロジェクトの設計書（`AGENTS.md` など）や、プロジェクト固有の別の Skill とこの Skill が食い違う場合は、プロジェクト側の記述を優先する。食い違いに気づいたら、そのことを伝える。
- 新しいプロジェクトでスタイルの土台を作るときは、`assets/` のひな形を使う（「assets」の節を参照）。
- 1〜9 節は原則で、どのプロジェクトでも守る。「好み」の節は作者の流儀なので、プロジェクトに別の指示があればそちらに従う。

## 1. 優先順と詳細度

- 優先順は詳細度ではなく、`@layer` の順序と記述順で決める。
- セレクタの詳細度は [0,1,0]（クラス 1 つ）を基本にする。状態（`:hover`、`[aria-expanded]` など）を重ねたときに限り、[0,2,0] まで許す。
- 次は使わない。
  - `!important`
  - ID セレクタ
  - 型で修飾したセレクタ（`div.c-foo`）
- [0,1,0] を超えそうなときは、詳細度を上げずに次のどれかで解決する。
  - **条件を `:where()` に入れる。** 「どういうときに」を `:where()` の中に、「何を」をその外に置く。

    ```css
    /* [0,1,0]。.c-menu を対象にしたほかのルールと同じ土俵で並ぶ */
    :where(.c-menu-toggle[aria-expanded="false"]) + .c-menu {
      display: none;
    }
    ```

  - **対象の要素にクラスを与える。** `.c-menu a:hover`（[0,2,1]）ではなく、`.c-menu__link:hover`（[0,2,0]）にする。
  - **後ろのレイヤーへ移す。** 上書きが目的なら、これで足りる。
  - 要素セレクタは、7 節の例外の範囲でだけ使う。
- `style` 属性でスタイルを当てない。フレームワークのスコープ付き CSS（Astro の `<style>`、Vue の `<style scoped>` など）も使わない。理由は次の 3 つ。
  - スコープ用の属性セレクタが足され、詳細度が上がる。
  - レイヤーの外に出る。レイヤーに属さないスタイルは、どのレイヤーよりも強い。
  - 読み込み順をフレームワークが決めるので、記述順で管理できない。

  スタイルはスタイルシートのファイルに集める。スタイルガイドのような開発用のページだけは、例外にしてよい。

- ここまでのルールは Stylelint で検査する（`assets/stylelint.config.mjs`）。
  - `no-descending-specificity` は無効にする。記述順で管理する前提と合わないため。
  - 余白（4 節）と論理プロパティ（7 節）は、Stylelint では検査しない。書く側が守る。論理プロパティは、あえて使わない判断もあるため。

## 2. レイヤーと命名

- レイヤーは次の順に宣言する。後ろのレイヤーほど強い。

  ```css
  @layer reset, tokens, base, layout, components, utilities;
  ```

  | レイヤー     | 役割                                   |
  | ------------ | -------------------------------------- |
  | `reset`      | 要素の既定値をならす                   |
  | `tokens`     | トークン（カスタムプロパティ）の定義   |
  | `base`       | 素の要素の既定のスタイル、言語別の組版 |
  | `layout`     | 中身によらない配置の入れ物             |
  | `components` | 固有の見た目を持つ部品                 |
  | `utilities`  | 例外的な、単機能の上書き               |

- `reset` / `tokens` / `base` ではクラスを定義しない。要素セレクタ、属性セレクタ、カスタムプロパティだけを扱う。
- 部品の中の要素は、BEM 風に `__要素` で表す。バリエーションは `--modifier` で表す（`.c-card__title`、`.c-card--wide`）。
- modifier は、見た目を変えたい要素そのものに付け、1 クラスで完結させる（`.c-list__label--date`）。
  - `.c-list--compact .c-list__label` のような組み合わせのセレクタは書かない。
  - block の modifier で `__要素` の見た目を変えたいときは、`--_` 変数を使う（6 節）。
- utilities には、意味を持たない単機能のものだけを置く（`.u-visually-hidden` など）。増やしすぎると、部品の責務が曖昧になる。
- components の中の記述順は「上書きされる側を先に、上書きする側を後に」。
  - 先に置く：ほかの部品に埋め込まれたり、mix されたりして上書きされうる部品（アイコン、見出し、`.c-prose` など）。mix とは、1 つの要素に、部品のクラスと親の部品の `__要素` クラスを並べて付けること（4 節）。
  - 後に置く：それを使って上書きする側（`__要素` を与える親の部品など）。

## 3. layout と components

- layout は「何を入れても成立する入れ物（並べ方）」、components は「固有の見た目を持つ部品」。
- layout の基本部品は、メディアクエリを使わず、中身の幅で並びが変わるように作る。実装例は `assets/layout.css`。

  | クラス       | 役割                                                           |
  | ------------ | -------------------------------------------------------------- |
  | `.l-stack`   | 対等な子を縦に積む                                             |
  | `.l-cluster` | 子を横に並べ、入りきらなければ折り返す                         |
  | `.l-grid`    | 同じ幅の子を格子状に並べる。1 列の最小幅だけを決め、列数は自動 |
  | `.l-split`   | 幅の違う 2 つを横に並べ、幅が足りなければ縦に積む              |

- layout の調整値（格子の最小幅など）は、`style` 属性ではなくクラスで変える。
  - その場所だけの調整なら、親の部品の `__要素` クラスを mix して、プロパティを直接書く（6 節）。
  - 同じ調整を 2 か所以上で使いたくなったら、layout の modifier（`.l-grid--narrow`）に昇格させる。1 か所のための modifier を増やすと、ユーティリティの寄せ集めに近づくため。
  - インブラウザデザインでは、まず直接書き、繰り返しが分かったら昇格させる。
- 共通化するかどうかは、「同じ理由で一緒に変わるか」で判断する。
  - 並べ方だけが同じなら、layout でまとめる。
  - 見た目も同じなら、components でまとめる。
  - 見た目が固まる前は、無理にまとめない。
- スタイルは少なく、具体的すぎない指定にする。共通のスタイルにまとめられるものは、まとめる。

## 4. 余白

前提として、ブラウザの既定のスタイルには妥当性がある。`p` には余白があり、見出しにはレベルに応じた大きさと余白がある。文脈の余白は、この考え方を前側だけに整理したもの。

### 2 種類の余白

| 種類       | 意味                                             | 付け方                                      |
| ---------- | ------------------------------------------------ | ------------------------------------------- |
| 配置の余白 | 対等な子どうしの間隔                             | 親の `gap`（layout、または部品の block）    |
| 文脈の余白 | 前の内容との意味上の距離。区切りが大きいほど広い | 子の `__要素` クラスの `margin-block-start` |

- どちらを使うかは親が決める。判断の基準は、「子どうしの間隔が、次に何が来るか（役割）で変わるか」。
  - 並び順がテンプレートで決まっている対等な並び（セクションの見出し・リード文・中身など）は、配置の余白でよい。
  - 文脈の余白が効くのは、中身の種類や順序が変わる場所（見出し・段落・リンクが入れ替わる本文の列など）。要素が増えたり減ったりしても、親の指定を直さずに済む。
- 1 つの入れ物の中で、2 種類を混ぜない。grid / flex の子の `margin` は相殺されず、`gap` に足されるため。文脈の余白で組む部品は `gap` を使わず、通常のブロックの流れで組む。

### margin の書き方

- 外側の余白（`margin`）は、`__要素` クラスにだけ書く。block や layout のクラスには書かない。
  - 部品は自分の外側の余白を持たない。置かれた先の親の部品が、`__要素` クラスで与える（BEM の mix）。
  - `padding` と `gap` は block に書いてよい。
  - 例外は 2 つ。位置合わせのための `auto`（`margin-inline: auto`、`margin-block-start: auto`）と、utilities の技術的な指定（視覚的に隠すための `margin: -1px` など）。
- 文脈の余白は、前側（`margin-block-start` / `margin-inline-start`）にだけ付ける。上から下へ流れるなら上、左から右へ流れるなら左。後ろ側には付けない。
- 流れの先頭の要素の余白は、入れ物の側で消す。
  - 打ち消しは同じ詳細度なので、その block の定義の最後に書き、記述順で勝たせる。
  - そのために、余白を持つ側の詳細度も [0,1,0] に保つ。

```html
<div class="c-article">
  <h2 class="c-heading c-article__heading">見出し</h2>
  <p class="c-article__text">段落</p>
  <p class="c-article__text">段落</p>
  <p class="c-article__more"><a href="#">もっと見る</a></p>
</div>
```

```css
.c-article__heading {
  margin-block-start: calc(var(--space) * 2);
}

.c-article__text {
  margin-block-start: var(--space);
}

.c-article__more {
  margin-block-start: calc(var(--space) * 1.5);
}

/* 流れの先頭には余白を付けない（最後に書いて、記述順で勝たせる） */
.c-article > :where(:first-child) {
  margin-block-start: 0;
}
```

- 先頭の打ち消しで消せるのは、直下の子だけ。包まれた孫の `margin` は、相殺によって包んだ要素の上端に出てくる。`margin-trim` が将来の代わりになりうるが、現状は Safari だけが対応している。
- 配置の余白で一部だけ間隔を変えたいときは、子に `margin` を足さない。まとまりごとに要素で包み、包んだ要素の中で別の `gap` を持たせる。

## 5. デザイントークン

- 基準となる値だけをトークン（`:root` のカスタムプロパティ）にする。派生する値は、スタイル側で `calc()` や相対色構文を使って作る。

  ```css
  padding: calc(var(--space) * 1.5);
  background: oklch(from var(--color-foreground) l c h / 8%);
  ```

- トークンにするのは、次のどれかに当てはまる値だけ。
  - ブランドとして決める値（1 か所を変えれば、全体が追従してほしいもの）
  - デザインシステムの芯として、ほかのサイトへ持ち出す値
  - ファイルをまたいで、互いの関係を保つ必要がある値（重なり順など）
- 色は「基準色」と「役割」の 2 段にする。
  - 基準色：`--color-black`、`--color-white` など
  - 役割：`--color-foreground`、`--color-background`、`--color-accent` など。派生値ではなく、どの基準色をどの役割に使うかの対応づけ。ダークモードやほかのサイトへの展開では、この対応づけを差し替える。
- 例外として、何度も使う派生の色（区切り線、薄い文字）だけは、役割として名前を付けてよい（`--color-border`、`--color-muted`）。
  - 注意：`:root` で計算した派生トークンは、計算後の値が継承される。ある要素の中で元の役割トークンを差し替えても、追従しない。必要なら、その要素で派生トークンも定義し直す。
- 文字サイズはトークンにしない。単位で基準を書き分ける。`px` は使わない。
  - `rem`：ベースから決まる段階（見出し・本文・小さい文字など）
  - `em`：周りの文字に比例させたいもの（補足のラベルなど）
  - 体系（基準値のトークンや、`pow()` による段階）は、使う値が固まってから決める。
- 重なり順は `--z-*` のトークンにし、全体の前後関係を 1 か所で見渡せるようにする。あとから層を差し込めるよう、値には余裕を持たせる。
- 相対色構文で有彩色の明度（`l`）を大きく動かすと、色域の外に出て、ブラウザによって見た目が変わることがある。その場合は `color-mix()` と組み合わせる。
- ブレークポイントはトークンにできない。`@media` の条件には `var()` を書けず、`@custom-media` もまだ実装されていないため。数値は直接書き、使っている値と場所を設計書の一覧表で管理する。

## 6. ローカル変数（`--_`）

- ある部品の中だけで使う調整用の値は、トークンと区別して `--_` で始め、名前に block 名を含める（`--_grid-min`、`--_stack-gap`、`--_heading-size`）。ほかのファイルや部品からも使いたくなったら、トークンに昇格させる。
  - block 名には、接頭辞（`l-`、`c-`）を付けない。
  - 自分の宣言でしか使わない変数も含める。「子に読ませるか」「mix されるか」を、書くたびに判断しなくて済むようにするため。
  - 含める理由は、同じ要素に複数の block のクラスが付く（mix）ことがあるため。同名の変数を 2 つの block が定義すると、後ろのレイヤーの値が勝ち、前の block 自身の宣言にもその値が効いてしまう。エラーにはならず、見た目だけが静かにずれる。
  - mix した `__要素` は、DOM の上では別の block の内側に置かれうる。変数は一番近い祖先の定義を読むので、同名の変数があると、読むつもりの block ではなく、内側の block の値になる。
- `--_` 変数は、同じ block の `__要素` からなら参照してよい。block の modifier 1 つで、要素の見た目を [0,1,0] のまま切り替えられる。

  ```css
  .c-heading {
    --_heading-size: 1.5rem;
  }

  .c-heading__title {
    font-size: var(--_heading-size);
  }

  .c-heading--minor {
    --_heading-size: 1.125rem;
  }
  ```

  子に読ませるときの約束：
  - 別の部品からは読まない。
  - 既定値は必ず block 側で定義する。

- block 自身の modifier では、宣言を書き直さず、`--_` 変数の値を差し替える（`.l-grid--narrow { --_grid-min: 9rem; }`）。先頭の打ち消しのように、宣言の順序に頼る指定を崩さないため。
- ほかの部品から調整するときは、相手の `--_` 変数には触らない。`__要素` クラスを mix してプロパティを直接書き、後ろのレイヤーか、後ろの記述順で勝たせる。

  ```html
  <div class="l-stack c-article__body">…</div>
  ```

  ```css
  /* components は layout より後ろのレイヤーなので勝つ */
  .c-article__body {
    gap: calc(var(--space) * 2);
  }
  ```

## 7. 素の要素と組版

- 要素セレクタは基本的に使わず、要素にクラスを付ける。`:where()` で詳細度を保てる場合も同じ。
  - 例外は、すべての要素にクラスを付けるのが現実的でない場合だけ。
    - reset / base
    - クラスのない HTML（Markdown や CMS が出力する本文）を包む `.c-prose` の中
    - 表のセル（`.c-table :where(th, td)`）
  - 例外でも `:where()` で包み、[0,1,0] に保つ。
- `.c-prose` は、クラスのない HTML に、要素セレクタで見た目と文脈の余白を与える部品。余白は 4 節に沿って前側にだけ付け、値は `--_prose-*` 変数で持つ。

  ```css
  .c-prose {
    --_prose-space: var(--space);
    --_prose-space-heading: calc(var(--space) * 2);
  }

  .c-prose > :where(*) {
    margin-block-start: var(--_prose-space);
  }

  .c-prose > :where(h2, h3) {
    margin-block-start: var(--_prose-space-heading);
  }

  .c-prose > :where(:first-child) {
    margin-block-start: 0;
  }
  ```

- `.c-prose` の中の要素に、クラスを付けて見た目を足さない。付けたくなった時点で、それは prose ではない。4 節の文脈の余白で組む、別の部品にする。部品を丸ごと埋め込むのはよい。
- リンクには既定で下線を付け、不要な部品の側で消す。クラスを付けられない本文中のリンクでも、リンクだと分かるようにするため。
- リストの記号と字下げはリセットしない。`margin` だけを 0 にする。
  - 入れ子で記号が disc → circle → square と変わる、ブラウザの既定を残すため。
  - 記号が要らないリストは、部品や layout の側で `list-style: none` と `padding-inline-start: 0` を指定する。
  - 「クラスの有無で見た目が変わる」ような、暗黙のルールは作らない。思い出しにくいため。
  - リンクの下線と同じく、「既定を残し、不要な部品の側で消す」という考え方。
- 論理プロパティ（`margin-block-start`、`inline-size` など）を原則として使う。物理プロパティ（`margin-top`、`width` など）は、意図がある場合だけ使う。
- hover の表現は、hover できる環境だけに限る（`@media (hover: hover)`）。タッチ端末では、別の手段で操作できるようにする。
- 言語ごとの組版（行間、`line-break`、`hyphens` など）は、`lang` 属性を起点に CSS で切り替える。部品のロジック（`locale === "ja" ? … : …`）に持ち込まない。
  - `:lang()` ではなく、`:where([lang|="ja"])` で書き、子へは継承で届ける。
  - `:lang()` は子孫のすべてに直接当たるので、親で値を変えても、子には継承されなくなる。

## 8. ブラウザサポート

Baseline の状況は時期によって変わる。判断するときは、その時点の状況を確かめる。

- Baseline Widely available の機能（ネスト、`@layer`、`:has()`、コンテナクエリなど）は、フォールバックなしで使う。ビルド時の変換（PostCSS など）は入れない。
- Newly available の機能は、公開時期と照らして、使うかどうかを個別に判断する（例：相対色構文）。使うと決めたら、理由と時期を設計書に残す。
- `var()` を含む宣言は、読み込み時の構文チェックを通ってしまう。そのため、「同じプロパティを 2 回書く」フォールバックは効かない。フォールバックが必要なら、`@supports` で囲む。

## 9. 作業環境

- スタイルガイドのページを、作業場として置く。
  - トークンの一覧は、CSS のファイルから自動で抽出する。手で書き写すと、実物とずれていくため。
  - 部品の見本は、要素の有無の組み合わせごとに並べる。部品やバリエーションを増やしたら、見本も足す。
- DevTools で、スタイルの出どころを追えるようにする。
  - 開発時は、CSS のソースマップを出す。
  - ビルドで、CSS を HTML にインライン化しない。

## 好み

作者の流儀。ほかの人やプロジェクトで使うときは、この節を書き換える。

- クラス名の接頭辞を、レイヤー名に対応させる（`.l-` = layout、`.c-` = components、`.u-` = utilities）。クラス名を見れば、どのレイヤーに属し、何に勝つかが分かる。
- Tailwind などの、ユーティリティファーストのフレームワークは使わない。
- CSS のファイルは少なく保つ。1 レイヤー 1 ファイルでも、`global.css` 1 つでもよい。分け方は、作業しながら変える。`@import` の並び順が、そのまま記述順になる。
- `--font-size-sm` のような、「派生値に名前を付けただけのトークン」は作らない。
- トークンに、サイト固有の接頭辞（`--xx-`）を付けない。`calc()` や `var()` を多用するので、入力の手間を優先する。
- 見た目は、あとで人がブラウザ上で詰める前提。AI が書くスタイルは仮のものとして、シンプルに、あとから編集しやすく書く。
- どのレイヤーに置くか、トークンにするかで迷ったら、決めずに相談する。

## プロジェクトごとに決めること

この Skill では決めない。プロジェクトの設計書に書く。

- トークンの具体的な値（色、書体、余白の基準値など）
- ブレークポイントの値と、その書き方
- セクションの上下の余白を、どのレイヤーに置くか
- 個々の部品の設計
- フレームワークの設定の細部

## assets（ひな形）

新しいプロジェクトで、スタイルの土台を作るときにコピーして使う。値はすべて仮。

| ファイル               | 内容                                                        |
| ---------------------- | ----------------------------------------------------------- |
| `stylelint.config.mjs` | 1 節のルールの検査。`stylelint-config-standard` が必要      |
| `global.css`           | レイヤーの順序の宣言と `@import`                            |
| `tokens.css`           | トークンの骨組み                                            |
| `layout.css`           | layout の基本部品（stack / cluster / grid / split）の実装例 |

## 書き終えたら確認すること

- 詳細度が [0,1,0]（状態を重ねた場合は [0,2,0]）を超えていないか。
- block や layout のクラスに、`margin`（`auto` 以外）を書いていないか。
- 文脈の余白を、後ろ側に付けていないか。先頭の打ち消しを、block の定義の最後に書いたか。
- 1 つの入れ物の中で、`gap` と子の `margin` を混ぜていないか。
- 派生値をトークンにしていないか。
- 物理プロパティを、意図なく使っていないか。
- Stylelint が通るか。

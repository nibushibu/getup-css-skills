# getup-css：素の CSS の設計ルール

素の CSS でサイトを組むときのルール。プリプロセッサも、ユーティリティファーストのフレームワークも使わない。

優先順は `@layer` と記述順で管理し、詳細度を低く揃える。ねらいは、ブラウザ上で値を変えながらデザインを詰めていける（インブラウザデザイン）状態を保つこと。

## この Skill の使い方

- CSS を書く・直す前に、このファイルを読む。
- プロジェクトの設計書（`AGENTS.md` など）や、プロジェクト固有の別の Skill とこの Skill が食い違う場合は、プロジェクト側の記述を優先する。食い違いに気づいたら、そのことを伝える。
- 新しいプロジェクトでスタイルの土台を作るときは、`assets/` のひな形を使う（「assets」の節を参照）。
- この Skill を更新したときは、`CHANGELOG.md` の前回からの追加分を読み、「使っている側で直すこと」に従う。
- Skill `modern-web-guidance`（Chrome チームの、新しい Web 技術のガイド）が使えるなら、併用する。
  - 何で実現するか（どの機能を使うか、その Baseline の状況）は、modern-web-guidance で確かめる。モデルの記憶より新しい。
  - どう書いて置くか（レイヤー、詳細度、命名、トークン、余白、状態の持ち方）は、この Skill に従う。ガイドのコード例は、この Skill の決まりに合わせて書き直してから使う。
  - ブラウザサポートは 9 節の方針で判断する。
  - 使えないときは、この Skill だけで進め、Baseline の状況は自分で確かめる。
- 1〜10 節は原則で、どのプロジェクトでも守る。「好み」の節は作者の流儀なので、プロジェクトに別の指示があればそちらに従う。

## 1. 優先順と詳細度

- 優先順は詳細度ではなく、`@layer` の順序と記述順で決める。
  - 例外として、自分の状態（この節）と先頭の打ち消し（4 節）だけは、詳細度で勝たせる。どちらも、親からの指定に、記述順と関係なく勝たせたいもの。
- セレクタの詳細度は [0,1,0]（クラス 1 つ）を基本にする。
  - その要素自身の状態を重ねたときに限り、[0,2,0] まで許す。状態は、操作に応じた疑似クラス（`:hover`、`:focus-visible`、`:active` など）、フォームの状態（`:checked` など）、自分の状態を表す属性（`aria-*`、`data-*`、`open`）を指す（8 節）。
  - 状態を詳細度で上げるのは、状態が通常の見た目と、親からの mix（2 節）の両方に、記述順に関係なく勝つようにするため。mix する親のルールは後ろに書かれるので、記述順だけでは「状態が勝つ」ことを保証できない。
  - 状態を 2 つ以上重ねるときは、2 つ目からを `:where()` に入れ、[0,2,0] に保つ（`.c-tab[aria-selected="true"]:where(:hover)`）。
    状態を 1 つだけ重ねたルールとは詳細度が同じになるので、その後に書き、記述順で勝たせる。
  - ほかの要素の状態や文脈（親・兄弟）、構造の疑似クラス（`:first-child`、`:not()`、`:has()` など）は状態に含めない。`:where()` に入れる。
  - 例外として、流れの先頭の余白の打ち消し（`.c-article > :first-child`）は、`:where()` に入れずに [0,2,0] で書く（4 節）。
  - 疑似要素（`::before` など）で増える分（[0,0,1]）は数えない。疑似要素へのスタイルは、その要素自身ではなく疑似要素に当たるので、要素の詳細度の争いに加わらないため。
- 次は使わない。
  - `!important`
  - ID セレクタ
  - 型で修飾したセレクタ（`div.c-foo`）。詳細度が上がり、要素も固定してしまう。`:where()` に入れた型（`.c-foo:where(ul)`）は詳細度に数えないが、要素の固定には気をつける（7 節）
- [0,1,0] を超えそうなときは、詳細度を上げずに次のどれかで解決する。
  - **条件を `:where()` に入れる。** 「どういうときに」を `:where()` の中に、「何を」をその外に置く。

    ```css
    /* [0,1,0]。.c-menu を対象にしたほかのルールと同じ土俵で並ぶ */
    :where(.c-menu-toggle[aria-expanded="false"]) + .c-menu {
      display: none;
    }
    ```

    同じ条件のもとで、いくつかの対象に同じ宣言を当てるときは、条件を 1 回だけ書き、対象を `:is()` にまとめる。
    条件を対象ごとに書き並べると、条件を直すときに直し漏れが出るため。

    ```css
    /* 条件は 1 回だけ。:is() の中はすべてクラス 1 つなので、[0,1,0] のまま */
    :where([data-intro="pending"]) :is(.c-kv__title, .c-kv__lead, .c-kv__scroll) {
      opacity: 0;
    }
    ```

    - `:is()` の詳細度は、中でいちばん高いセレクタの詳細度になる。1 つでも高いものが混ざると、全体が上がる。
      そのため、`:is()` に入れるのはクラス 1 つのセレクタだけにする。Stylelint の詳細度の検査は、この上がった値で行われる。
    - 条件のない、ただの並び（`.c-a, .c-b`）は、カンマで並べたままにする。まとめても短くならないため。
    - `:is()` の中に、ブラウザが解釈できないセレクタがあっても、ルール全体は捨てられない（カンマの並びでは全体が捨てられる）。

  - **対象の要素にクラスを与える。** `.c-menu a:hover`（[0,2,1]）ではなく、`.c-menu__link:hover`（[0,2,0]）にする。
  - **後ろのレイヤーへ移す。** 上書きが目的なら、これで足りる。
  - 要素セレクタは、7 節に沿って `:where()` に入れて使う。要素に固定しなくてよい場面では、クラスで書く。
- `style` 属性でスタイルを当てない。フレームワークのスコープ付き CSS（Astro の `<style>`、Vue の `<style scoped>` など）も使わない。理由は次の 3 つ。
  - スコープ用の属性セレクタが足され、詳細度が上がる。
  - レイヤーの外に出る。レイヤーに属さないスタイルは、どのレイヤーよりも強い。
  - 読み込み順をフレームワークが決めるので、記述順で管理できない。

  スタイルはスタイルシートのファイルに集める。スタイルガイドのような開発用のページだけは、例外にしてよい。

- ここまでのルールは Stylelint で検査する（`assets/stylelint.config.mjs`）。
  - Stylelint は、方針が守られているかを確かめる補助で、方針そのものではない。方針はこの Skill の文言で決まる。
    検査で区別できないものは、書く側が守る。検査が方針より厳しく、方針どおりのセレクタがエラーになるときは、
    理由を書いた無効化コメントで通す（`/* stylelint-disable-next-line <ルール名> -- <理由> */`）。
    理由のない無効化コメントはエラーにする（`reportDescriptionlessDisables`）。
  - `no-descending-specificity` は無効にする。記述順で管理する前提と合わないため。
  - 余白（4 節）と論理プロパティ（7 節）は、Stylelint では検査しない。書く側が守る。論理プロパティは、あえて使わない判断もあるため。
  - 詳細度は [0,2,1] を上限として検査する。上の [0,0,1] は、許している [0,2,0] に疑似要素を重ねた分（`.c-a:hover::before`）。
    その [0,2,0] が、許している 2 つ（自分の状態を重ねたもの、先頭の打ち消し）か、組み合わせのセレクタ（`.c-a .c-b`）かは区別できない。
    [0,0,1] が疑似要素か、要素セレクタ（`.c-menu a:hover`）かも区別できない。どちらも書く側が守る。
  - 型で修飾したセレクタは `selector-no-qualifying-type` で検査する。このルールは `:where()` の中の型（`.c-foo:where(ul)`）も
    エラーにするので、7 節に沿って使う場合は、無効化コメントで通す。

## 2. レイヤーと命名

- レイヤーは次の順に宣言する。後ろのレイヤーほど強い。

  ```css
  @layer reset, tokens, base, layout, components, utilities;
  ```

  | レイヤー     | 役割                                   |
  | ------------ | -------------------------------------- |
  | `reset`      | 要素の既定値をならす                   |
  | `tokens`     | トークン（カスタムプロパティ）の定義   |
  | `base`       | 素の要素の既定のスタイル、言語別の組版 |
  | `layout`     | 中身によらない配置の入れ物             |
  | `components` | 固有の見た目を持つ部品                 |
  | `utilities`  | 例外的な、単機能の上書き               |

- `reset` / `tokens` / `base` ではクラスを定義しない。要素セレクタ、属性セレクタ、カスタムプロパティだけを扱う。
- 素の要素は、外側の余白（`margin`）を持たない。
  - ブラウザが既定で付ける `margin`（`body`、見出し、段落、リスト、`blockquote`、`figure`、`hr` など）は、`reset` で 0 にする。
  - `base` でも `margin` は付けない。余白は、置かれた場所に応じて親の側から与える（4 節）。
  - 位置合わせのための `auto`（`dialog` の中央寄せなど）は、ブラウザの既定のまま残す。
- 部品の中の要素は、BEM 風に `__要素` で表す。バリエーションは `--modifier` で表す（`.c-card__title`、`.c-card--wide`）。
- modifier は、見た目を変えたい要素そのものに付け、1 クラスで完結させる（`.c-list__label--date`）。
  - `.c-list--compact .c-list__label` のような組み合わせのセレクタは書かない。
  - block の modifier で `__要素` の見た目を変えたいときは、`--_` 変数を使う（6 節）。
- utilities には、意味を持たない単機能のものだけを置く（`.u-visually-hidden` など）。増やしすぎると、部品の責務が曖昧になる。
- components の中の記述順は「上書きされる側を先に、上書きする側を後に」。
  - 最初に置く：`.c-prose` と `.c-prose-end`（7 節）。`.c-prose-end` の打ち消しは、それより前に書いた部品の指定まで消してしまうため。
  - 先に置く：ほかの部品に埋め込まれたり、mix されたりして上書きされうる部品（アイコン、見出しなど）。mix とは、1 つの要素に、部品のクラスと親の部品の `__要素` クラスを並べて付けること（4 節）。
  - 後に置く：それを使って上書きする側（`__要素` を与える親の部品など）。

## 3. layout と components

- layout は「何を入れても成立する入れ物（並べ方）」、components は「固有の見た目を持つ部品」。
- layout の基本部品は、メディアクエリを使わず、中身の幅で並びが変わるように作る。実装例は `assets/layout.css`。

  | クラス        | 役割                                                                                     |
  | ------------- | ---------------------------------------------------------------------------------------- |
  | `.l-stack`    | 対等な子を縦に積む                                                                       |
  | `.l-cluster`  | 子を横に並べ、入りきらなければ折り返す                                                   |
  | `.l-grid`     | 同じ幅の子を格子状に並べる。1 列の最小幅だけを決め、列数は自動                           |
  | `.l-switcher` | 子をすべて横に並べ、幅が足りなければすべて縦に積む（途中の列数を通らない）               |
  | `.l-split`    | 幅の違う 2 つを横に並べ、幅が足りなければ縦に積む。狭い側を中身の幅にする `--fit` もある |

- layout の調整値（格子の最小幅など）は、`style` 属性ではなくクラスで変える。
  - その場所だけの調整なら、親の部品の `__要素` クラスを mix して、プロパティを直接書く（6 節）。
  - 同じ調整を 2 か所以上で使いたくなったら、layout の modifier（`.l-grid--narrow`）に昇格させる。1 か所のための modifier を増やすと、ユーティリティの寄せ集めに近づくため。
  - インブラウザデザインでは、まず直接書き、繰り返しが分かったら昇格させる。
- 並びを切り替えるしきい値（格子の 1 列の最小幅、`.l-split` の広い側の下限など）は、layout が持つ値で、block が自分の大きさを持つこと（下）とは別のもの。
  - メディアクエリを使わない layout でも、どこで切り替えるかの値は 1 つ要る。CSS は、どこまで細くすると読みにくいかを知らないため。
  - できるだけ中身に比例する単位（`em`、`ch`）で書き、値の意味を説明できるようにする（`32em` は「和文の 1 行が 32 字を下回るなら積む」）。
- 共通化するかどうかは、「同じ理由で一緒に変わるか」で判断する。
  - 並べ方だけが同じなら、layout でまとめる。
  - 見た目も同じなら、components でまとめる。
  - 見た目が固まる前は、無理にまとめない。
- layout と components は、名前で見分ける。
  - layout は並べ方で名付け、中身のことを言わない（`.l-stack`、`.l-cluster`）。components は中身や意味で名付ける（`.c-post-list`、`.c-link-list`）。
  - 迷ったら「中身に触れずに名前を付けられるか」で確かめる。付けられるなら layout、中身の名前が自然に出てくるなら components。
- layout に切り出すのは、同じ並べ方が、違う中身で 2 か所目に出てきたとき。
  - 最初は、中身の名前で component として書き、並べ方もその中に書いてよい。
  - 同じ部品を 2 か所で使うのは、component の使い回しで、layout に切り出す理由にはならない。
  - 切り出したら、並べ方の名前で layout にし、component と mix する（`<ul class="l-cluster c-link-list">`）。component には、中身に固有のことだけを残す。何も残らなければ、component のクラスは外す。
  - 並べ方と見た目が一緒に変わるなら（区切り線の位置を `gap` から計算しているなど）、分けない。
- block や layout は、自分の置かれ方を持たない。置かれ方とは、親の並びの中でのふるまい（外側の `margin`、`align-self`、`justify-self`、`flex`、`order`、`grid-column`、`grid-row` など）のこと。
  - 置かれた先の親が、`__要素` クラスで与える（BEM の mix）。親の側の `> *` で、子に一律に与えてもよい（`assets/layout.css` の `.l-split`）。
  - 同じ部品でも、置かれる親によって伸び方や位置が変わるため。外側の `margin` の決まり（4 節）は、この一部。
  - 例外は、4 節と同じく、位置合わせのための `margin` の `auto`。
- block は、自分の大きさ（幅と高さ）を固定の値で持たない。大きさは、中身の大きさか、親の並べ方で決まるようにする。
  - 置かれ方と同じく、置かれた先によって使える幅が変わるため。固定の幅を持つ部品は、置ける場所が限られる。
  - その場所での幅（固定の幅、上限、下限）は、置かれた先の親が `__要素` クラスで与える。同じ幅の決め方を繰り返し使うなら、layout にする（`assets/layout.css` の `.l-container` の最大幅、`.l-split__side` の基準の幅）。
  - block の中の `__要素` の幅は、block が自分の中の並べ方として決めてよい。block は、その要素の親にあたるため。
  - 文章の行の長さ（読みやすさのための `max-inline-size`）も、親が与える。隣に何かが並ぶ場所では邪魔になり、ページの幅いっぱいの列では必要になるなど、置かれた先で要否が変わるため。
  - block が自分で持ってよいのは、次の値だけ。
    - 中身に比例する値：アイコンの `1em`、`aspect-ratio` など。
    - 下限：押しやすさのための最小の大きさ、flex や grid の子を縮められるようにする `min-inline-size: 0` など。縮めると壊れる限界を書くだけで、伸び方は縛らない。
    - 親の並びの外に出る部品の幅：ダイアログやポップオーバーなど、幅を決める親がないもの。`min(100% - 余白, 40rem)` のように、画面に収まる形で書く。
    - 中身の大きさを持たない飾りの大きさ：中が空の丸など、大きさがそのまま見た目になるもの。`em` か、トークンからの派生で書く。
- スタイルは少なく、具体的すぎない指定にする。共通のスタイルにまとめられるものは、まとめる。

## 4. 余白

前提として、ブラウザの既定のスタイルの考え方には妥当性がある。`p` には余白があり、見出しにはレベルに応じた大きさと余白がある。ただし、既定の余白は要素自身が前後の両側に持つので、置かれた場所に合わせて変えにくい。

そこで、既定の余白は `reset` で 0 にし（2 節）、文脈の余白として、前側だけに、親の側から与え直す。クラスのない HTML（Markdown の本文など）には、`.c-prose` で与える（7 節）。

### 2 種類の余白

| 種類       | 意味                                             | 付け方                                      |
| ---------- | ------------------------------------------------ | ------------------------------------------- |
| 配置の余白 | 対等な子どうしの間隔                             | 親の `gap`（layout、または部品の block）    |
| 文脈の余白 | 前の内容との意味上の距離。区切りが大きいほど広い | 子の `__要素` クラスの `margin-block-start` |

- どちらを使うかは親が決める。判断の基準は、「子どうしの間隔が、次に何が来るか（役割）で変わるか」。
  - 並び順がテンプレートで決まっている対等な並び（セクションの見出し・リード文・中身など）は、配置の余白でよい。
  - 文脈の余白が効くのは、中身の種類や順序が変わる場所（見出し・段落・リンクが入れ替わる本文の列など）。要素が増えたり減ったりしても、親の指定を直さずに済む。
- 1 つの入れ物の中で、2 種類を混ぜない。grid / flex の子の `margin` は相殺されず、`gap` に足されるため。文脈の余白で組む部品は `gap` を使わず、通常のブロックの流れで組む。

### margin の書き方

- 外側の余白（`margin`）は、`__要素` クラスにだけ書く。block や layout のクラスには書かない。
  - 部品は自分の外側の余白を持たない。置かれた先の親の部品が、`__要素` クラスで与える（BEM の mix）。外側の余白は、置かれ方（3 節）の 1 つ。
  - 素の要素にも、`reset` / `base` で余白を付けない（2 節）。クラスのない HTML の余白は、`.c-prose` が与える（7 節）。
  - `padding` と `gap` は block に書いてよい。
  - 例外は 2 つ。位置合わせのための `auto`（`margin-inline: auto`、`margin-block-start: auto`）と、utilities の技術的な指定（視覚的に隠すための `margin: -1px` など）。
- 文脈の余白は、前側（`margin-block-start` / `margin-inline-start`）にだけ付ける。上から下へ流れるなら上、左から右へ流れるなら左。後ろ側には付けない。
- 流れの先頭の要素の余白は、入れ物の側で消す。
  - 打ち消しは `:where()` に入れず、`.c-article > :first-child`（[0,2,0]）で書く。詳細度で `__要素` の余白（[0,1,0]）に勝つので、記述順に関係なく、block の定義の中にまとめて書ける。
  - 余白を持つ側は [0,1,0] のままにする。状態を重ねて [0,2,0] にした余白は、記述順によっては打ち消しに勝ってしまう。

```html
<div class="c-article">
  <h2 class="c-heading c-article__heading">見出し</h2>
  <p class="c-article__text">段落</p>
  <p class="c-article__text">段落</p>
  <p class="c-article__more"><a href="#">もっと見る</a></p>
</div>
```

```css
.c-article {
  /* 流れの先頭には余白を付けない（詳細度で勝つので、block の定義の中に書いてよい） */
  & > :first-child {
    margin-block-start: 0;
  }
}

.c-article__heading {
  margin-block-start: calc(var(--space) * 2);
}

.c-article__text {
  margin-block-start: var(--space);
}

.c-article__more {
  margin-block-start: calc(var(--space) * 1.5);
}
```

- 先頭の打ち消しで消せるのは、直下の子だけ。包まれた孫の `margin` は、相殺によって包んだ要素の上端に出てくる。`margin-trim` が将来の代わりになりうるが、現状は Safari だけが対応している。
- 配置の余白で一部だけ間隔を変えたいときは、子に `margin` を足さない。まとまりごとに要素で包み、包んだ要素の中で別の `gap` を持たせる。

### 余白の大きさ

`margin`、`padding`、`gap` のどれにも当てはまる。

- 余白の大きさを何に合わせるか（全体で揃えるか、文字サイズに比例させるか、その間をとるか）は、余白ごとに決める。どれかに統一することは求めない。
  - `--space` から `calc()` で作る：文字サイズに関係なく一定になり、`--space` を変えれば全体が追従する。
  - `em` で書く：その要素の文字サイズに比例する。ボタンの内側の余白を、文字サイズを起点に決めるときなど。
  - 混ぜる、範囲を付ける：`calc()` で `em` と `--space` を足し合わせる。`max()`、`min()`、`clamp()` で上限や下限を付ける。画面幅（`vw`）と組み合わせる。
- 変数に `em` を入れると、変数を定義した要素ではなく、使った要素の文字サイズで計算される（`--_prose-space: 1em` は、prose の中の h2 では h2 の文字サイズになる）。

### はみ出し（負の margin）

部品の中の要素を、親の `padding` の分だけ外へはみ出させることがある。背景や画像を親の端まで広げたり、リンクのクリック領域を広げたりするとき。2 種類の余白とは別の、余白を打ち消す手法として扱う。

- 4 節のほかの `margin` と同じく、`__要素` クラスに書く。
- 値は、親の `padding` と同じ変数から取る。数値を直接書かず、親の余白を変えたときに追従させる。同じ部品の中なら block の `--_` 変数を、部品をまたぐなら引数（6 節）を使う。
- 中身の位置を保ちたいとき（クリック領域だけを広げるなど）は、同じ量の `padding` を組にする。

  ```css
  .c-menu {
    --_menu-inset: var(--space);

    padding-inline: var(--_menu-inset);
  }

  /* 背景は親の端まで広げ、文字の位置は保つ */
  .c-menu__link {
    margin-inline: calc(-1 * var(--_menu-inset));
    padding-inline: var(--_menu-inset);
  }
  ```

- ブロック方向の先頭（`margin-block-start`）へのはみ出しは、流れの先頭の打ち消しとぶつかり、詳細度で打ち消しに負ける。先頭の要素を親の上端まで広げたいときは、親の `padding-block-start` を 0 にするなど、ほかの方法をとる。

## 5. デザイントークン

- 基準となる値だけをトークン（`:root` のカスタムプロパティ）にする。派生する値は、スタイル側で `calc()` や相対色構文を使って作る。

  ```css
  padding: calc(var(--space) * 1.5);
  background: oklch(from var(--color-foreground) l c h / 8%);
  ```

- トークンにするのは、次のどれかに当てはまる値だけ。
  - ブランドとして決める値（1 か所を変えれば、全体が追従してほしいもの）
  - デザインシステムの芯として、ほかのサイトへ持ち出す値
  - ファイルをまたいで、互いの関係を保つ必要がある値（重なり順など）
- トークンの名前は「分類」と「役割」で作る（`--color-foreground`、`--space-page`、`--z-header`）。
  - 分類は値の種類にする（`color`、`space`、`font`、`shadow`、`z`）。名前の先頭に置き、引数（block 名で始まる。6 節）と見分ける。
  - 役割は、その値がデザインの上で何を表すかにする（前景、ページの端からの距離、ヘッダーの重なり）。具体的でよい。
  - 分類の中で、ほかの値の元になる値は、役割を付けずに分類名だけでよい（`--space` から `calc(var(--space) * 1.5)` を作る）。
  - 名前で、値をどのプロパティに置くかを決めない（`--page-padding` ではなく `--space-page`）。同じ値をほかのプロパティで使うと、名前と使い方が合わなくなるため（`gap: var(--page-padding)`）。どのプロパティで空けるかは、部品の側で決める（4 節）。
    プロパティと同じ単語でも、置き場所ではなくデザインの上のもの（`--color-border` の区切り線）を指すならよい。
  - 迷ったら「この値をほかのプロパティで使っても、名前と使い方が合うか」で確かめる。
- 色は「基準色」と「役割」の 2 段にする。
  - 基準色：`--color-black`、`--color-white` など
  - 役割：`--color-foreground`、`--color-background`、`--color-accent` など。派生値ではなく、どの基準色をどの役割に使うかの対応づけ。ダークモードやほかのサイトへの展開では、この対応づけを差し替える。
- 例外として、何度も使う派生の色（区切り線、薄い文字）だけは、役割として名前を付けてよい（`--color-border`、`--color-muted`）。
  - 注意：`:root` で計算した派生トークンは、計算後の値が継承される。ある要素の中で元の役割トークンを差し替えても、追従しない。必要なら、その要素で派生トークンも定義し直す。
- 部品は、役割の色だけを使う。基準色や色の値を、部品に直接書かない（`currentcolor` と `transparent` はよい）。
  ライトとダークの両方に対応しないプロジェクトでも守る。あとから対応するとき、役割の対応づけを差し替えるだけで済む。
- 派生色は、明るさの向きを決め打ちしない。
  - 役割どうしを混ぜて作る。ライトでもダークでも、「背景を少し文字色に寄せる」という意味が保たれる。

    ```css
    background: color-mix(in oklch, var(--color-background) 90%, var(--color-foreground) 10%);
    ```

  - `oklch(from var(--color-background) calc(l - 0.05) c h)` のように明度を一方向に動かすと、ダークモードでは意図と逆になる。
- 方法の 1 つとして、役割の色を、色相と明暗の向きから計算してもよい。この方法では、基準色を置かない。

  ```css
  :root {
    --color-hue: 220deg;
    --color-direction: 1; /* ライトは 1、ダークは -1 */
    --color-background: oklch(calc(0.6 + 0.37 * var(--color-direction)) 0.01 var(--color-hue));
    --color-foreground: oklch(calc(0.55 - 0.35 * var(--color-direction)) 0.02 var(--color-hue));

    @media (prefers-color-scheme: dark) {
      --color-direction: -1;
    }
  }

  /* 背景から、文字色と反対の側へ一段ずらす */
  .c-card {
    background: oklch(from var(--color-background) calc(l + 0.05 * var(--color-direction)) c h);
  }
  ```

  - 向いているのは、ライトとダークの両方に対応し、配色が 1 つの色相でまとまるとき。ダークモードへの切り替えは、向きの値を反転するだけで済む。
  - 役割どうしを混ぜるだけでは作れない、「文字色と反対の側へずらす」派生を書ける。
  - ライトとダークの色を別々に選べない。ブランドとして決まった色の値や、複数の色相を使う配色には合わせにくい。
  - 使うなら、プロジェクトの設計書に書く。
- 文字サイズはトークンにしない。単位で基準を書き分ける。`px` は使わない。
  - `rem`：ベースから決まる段階（見出し・本文・小さい文字など）
  - `em`：周りの文字に比例させたいもの（補足のラベルなど）
  - 体系（基準値のトークンや、`pow()` による段階）は、使う値が固まってから決める。
- 重なり順は `--z-*` のトークンにし、全体の前後関係を 1 か所で見渡せるようにする。あとから層を差し込めるよう、値には余裕を持たせる。
- 相対色構文で有彩色の明度（`l`）を大きく動かすと、色域の外に出て、ブラウザによって見た目が変わることがある。その場合は `color-mix()` と組み合わせる。
- ブレークポイントはトークンにできない。`@media` の条件には `var()` を書けず、`@custom-media` もまだ実装されていないため。数値は直接書き、使っている値と場所を設計書の一覧表で管理する。

## 6. ローカル変数（`--_`）と引数

- ある部品の中だけで使う調整用の値は、トークンと区別して `--_` で始め、名前に block 名を含める（`--_grid-min`、`--_stack-gap`、`--_heading-size`）。ほかのファイルや部品からも使いたくなったら、トークンに昇格させる。
  - block 名には、接頭辞（`l-`、`c-`）を付けない。
  - 自分の宣言でしか使わない変数も含める。「子に読ませるか」「mix されるか」を、書くたびに判断しなくて済むようにするため。
  - 含める理由は、同じ要素に複数の block のクラスが付く（mix）ことがあるため。同名の変数を 2 つの block が定義すると、後ろのレイヤーの値が勝ち、前の block 自身の宣言にもその値が効いてしまう。エラーにはならず、見た目だけが静かにずれる。
  - mix した `__要素` は、DOM の上では別の block の内側に置かれうる。変数は一番近い祖先の定義を読むので、同名の変数があると、読むつもりの block ではなく、内側の block の値になる。
- `--_` 変数は、同じ block の `__要素` からなら参照してよい。block の modifier 1 つで、要素の見た目を [0,1,0] のまま切り替えられる。

  ```css
  .c-heading {
    --_heading-size: 1.5rem;
  }

  .c-heading__title {
    font-size: var(--_heading-size);
  }

  .c-heading--minor {
    --_heading-size: 1.125rem;
  }
  ```

  子に読ませるときの約束：
  - 別の部品からは読まない。
  - 既定値は必ず block 側で定義する。

- block 自身の modifier では、宣言を書き直さず、`--_` 変数の値を差し替える（`.l-grid--narrow { --_grid-min: 9rem; }`）。block の定義の中で、記述順に頼っている指定を崩さないため。
- ほかの部品から調整するときは、相手の `--_` 変数には触らない。`__要素` クラスを mix してプロパティを直接書き、後ろのレイヤーか、後ろの記述順で勝たせる。

  ```html
  <div class="l-stack c-article__body">…</div>
  ```

  ```css
  /* components は layout より後ろのレイヤーなので勝つ */
  .c-article__body {
    gap: calc(var(--space) * 2);
  }
  ```

- 直接書くだけでは足りないときは、部品が引数を用意する。引数は、ほかの部品から値を受け取るための変数で、`_` を付けず、block 名で始める（`--nav-inset`）。部品の中の複数の要素が、外から渡された同じ値を使うときに使う。親が部品の中の要素を指すセレクタを書かずに済む。

  ```css
  /* 部品の側：引数を内部の値で受け、既定値を 1 か所に書く */
  .c-nav {
    --_nav-inset: var(--nav-inset, 0);
  }

  .c-nav__item {
    padding-inline-start: var(--_nav-inset);
  }

  /* 親の側：部品の先頭の要素に `__要素` を mix して、引数を渡す */
  .c-site-header__nav {
    --nav-inset: var(--space);
  }
  ```

  ```html
  <nav class="c-nav c-site-header__nav">…</nav>
  ```

  引数の約束：
  - 部品の側では、引数を直接読まず、内部の値（`--_` 変数）で受ける。既定値は、そこで `var()` の第 2 引数として 1 か所にだけ書く。
  - 引数そのものは、部品の側で定義しない。定義すると、親が渡した値を上書きしてしまう。名前の違う内部の値で受ければ、親が祖先で渡しても、同じ要素（mix）で渡しても、記述順に関係なく親の値が届く。
  - 親は、部品の先頭の要素（mix）か、その祖先で渡す。部品の内側の要素で渡しても、先頭の要素で計算された内部の値には届かない。
  - 引数もトークンも `_` が付かないので、名前の始まりで見分ける。トークンは分類の名前（`--color-`、`--space` など）で始まり、トークンのファイルにだけ置く。引数は block 名で始まり、`:root` やトークンのファイルには置かない。
  - 考え方は、Lea Verou の pseudo-private の変数と、Open Props（`--_` を内部の値に使う）にならっている。`--_` の名前に block 名を含める点だけが違う。

## 7. 素の要素と組版

- 要素セレクタを避ける理由は 2 つ。詳細度を一定に保つためと、スタイルを要素に固定しないため。
  - 詳細度：要素セレクタは `:where()` に入れ、[0,1,0] に保つ。詳細度に数えられる形（`.c-menu a`、`div.c-foo`）では書かない。
  - 要素への固定：要素セレクタで書いたスタイルは、マークアップを変えると効かなくなる（`ul` を `ol` にする、`h2` を `h3` にするなど）。
    固定しなくてよい場面では、要素にクラスを付けて書く。部品の中の要素は、`__要素` クラスで表す（2 節）。
  - 要素セレクタを使うのは、要素にクラスを付けるのが現実的でない場面か、その要素であること自体に意味がある場面。例：
    - reset / base
    - クラスのない HTML（Markdown や CMS が出力する本文）を包む `.c-prose` の中
    - 表のセル（`.c-table :where(th, td)`）
  - どの場合も `:where()` で包み、[0,1,0] に保つ。先頭の打ち消しだけは、4 節のとおり `> :first-child`（[0,2,0]）で書く（`.c-prose` の入れ物の中の打ち消しを除く）。
- `.c-prose` は、クラスのない HTML に、要素セレクタで見た目と文脈の余白を与える部品。components の先頭に置く（2 節）。
  - 見た目（見出しの大きさ、区切り線など）は、直下の子に限らず、子孫の要素に当てる（`.c-prose :where(h2)`）。
  - `.c-prose` 自身には、継承されるプロパティ（`color`、`line-height` など）を書かない。継承された値は、`.c-prose-end` で打ち消せないため。
  - 余白は 4 節の文脈の余白として前側にだけ付け、値は `--_prose-*` 変数で持つ。付けるのは、直下の子と、流れを作る入れ物（`blockquote`、`li`、`dd`）の子。子孫すべてには付けない。行の中の画像などにも、上の余白が付いてしまうため。
  - 直下の子の先頭は、4 節のとおり `> :first-child`（[0,2,0]）で打ち消す。入れ物の中の先頭は `:where(:first-child)`（[0,1,0]）で打ち消し、余白の指定の後に置く。[0,2,0] にすると、`.c-prose-end` の打ち消しにも、埋め込んだ部品の余白にも勝ってしまうため。
  - 余白は、すべての子に付けて先頭を打ち消す。`* + *` では書かない。見出しの前を広くするような上書きで `* +` を書き忘れても、先頭は 0 に保たれる。4 節の部品とも書き方がそろい、`margin-trim` が使えるようになれば、打ち消しをそのまま置き換えられる。
  - 通常のブロックの流れのまま使う。flex や grid にしない（mix で変えることも含む）。`gap` と子の `margin` が混ざり（4 節）、`float` や余白の相殺も効かなくなるため。

  ```css
  /* components の先頭に置く（2 節） */
  .c-prose {
    --_prose-space: var(--space);
    --_prose-space-heading: calc(var(--space) * 2);

    /* 流れの先頭には余白を付けない（詳細度で勝つので、block の定義の中に書いてよい） */
    & > :first-child {
      margin-block-start: 0;
    }
  }

  /* 見た目は子孫の要素に当てる */
  .c-prose :where(h2) {
    font-size: 1.5rem;
  }

  /* 文脈の余白は、直下の子と、流れを作る入れ物の子に付ける */
  .c-prose > :where(*),
  .c-prose :where(blockquote, li, dd) > :where(*) {
    margin-block-start: var(--_prose-space);
  }

  .c-prose > :where(h2, h3) {
    margin-block-start: var(--_prose-space-heading);
  }

  /* 入れ物の中の先頭は [0,1,0] で打ち消し、余白の指定の後に置く */
  .c-prose :where(blockquote, li, dd) > :where(:first-child) {
    margin-block-start: 0;
  }

  /* prose の中に埋め込む部品から、prose の指定を打ち消す（.c-prose の直後に置く） */
  .c-prose-end :where(*) {
    all: revert-layer;
  }
  ```

- `.c-prose` の中の要素に、クラスを付けて見た目を足さない。付けたくなった時点で、それは prose ではない。4 節の文脈の余白で組む、別の部品にする。部品を丸ごと埋め込むのはよい。
- `.c-prose` の中に部品を埋め込むときは、`.c-prose-end` で包むか、部品に `.c-prose-end` を mix する。中の要素への prose の指定は、`all: revert-layer` で打ち消され、prose が当たる前の値（`base` と `layout` の値）に戻る。
  - `.c-prose-end` の要素自身は打ち消さない。prose の直下の子として、前の余白を受け取る。
  - 埋め込んだ部品の指定は、記述順で `.c-prose-end` より後ろにあるので、打ち消されない。`revert-layer` が働くのは、後ろの部品が指定していないプロパティだけ。
  - 打ち消されてしまうのは、`.c-prose-end` より前に書いた部品の指定と、[0,1,0] より詳細度の低い指定（セレクタ全体を `:where()` で包んだものなど）。前者は、`.c-prose` と `.c-prose-end` を components の先頭に置くことで防ぐ。
  - `.c-prose-end` の中にもう一度 `.c-prose` を置いても、内側の prose は効かない。`.c-prose-end` の打ち消しが、内側の prose の指定より後ろにあるため。この入れ子は作らない。
- リンクには既定で下線を付け、不要な部品の側で消す。クラスを付けられない本文中のリンクでも、リンクだと分かるようにするため。
- リストの記号と字下げはリセットしない。`reset` で 0 にするのは、ほかの要素と同じく `margin` だけ（2 節）。
  - 入れ子で記号が disc → circle → square と変わる、ブラウザの既定を残すため。
  - 記号が要らないリストは、部品や layout の側で `list-style: none` と `padding-inline-start: 0` を指定する。
  - 「クラスの有無で見た目が変わる」ような、暗黙のルールは作らない。思い出しにくいため。
  - リンクの下線と同じく、「既定を残し、不要な部品の側で消す」という考え方。
- 論理プロパティ（`margin-block-start`、`inline-size` など）を原則として使う。物理プロパティ（`margin-top`、`width` など）は、意図がある場合だけ使う。
- 言語ごとの組版（行間、`line-break`、`hyphens` など）は、`lang` 属性を起点に CSS で切り替える。部品のロジック（`locale === "ja" ? … : …`）に持ち込まない。
  - `:lang()` ではなく、`:where([lang|="ja"])` で書き、子へは継承で届ける。
  - `:lang()` は子孫のすべてに直接当たるので、親で値を変えても、子には継承されなくなる。

## 8. 状態と動き

- 開閉・選択・表示などの状態は、属性で表す。JS は属性を書き換えるだけにし、見た目は CSS が属性を見て決める。
  - 状態を表すクラス（`.is-open` など）は使わない。属性とクラスの両方で状態を持つと、ずれることがあるため。
  - 意味のある属性があれば、それを使う（`aria-expanded`、`aria-current`、`aria-selected`、`hidden`、`open` など）。支援技術にも同じ状態が伝わる。
  - 該当する属性がなければ、`data-*` 属性を使う。値は `aria-*` と同じく `"true"` / `"false"` の文字列にする。`"false"` で「JS が管理していて、まだその状態ではない」ことを表せる。
- ほかの要素の状態を条件にするときは、`:where()` に入れ、詳細度を保つ（1 節）。

  ```css
  :where(.c-menu-toggle[aria-expanded="false"]) + .c-menu {
    display: none;
  }
  ```

- JS が動いて初めて元に戻る見た目（画面に入るまで隠すなど）は、見えている状態を既定にする。隠す指定は `@media (scripting: enabled)` で囲み、JS が動かない環境で中身が消えないようにする。
- 画面に入ったときの出現や視差のような、装飾のための大きな動きは、`@media (prefers-reduced-motion: no-preference)` の中にだけ書く。動きを減らす設定の環境では、動かさずに最終の状態を見せる。開閉の矢印の回転のような、操作に応じた小さな変化までは対象にしない。

  ```css
  .c-feature__image {
    transition:
      opacity 0.6s,
      translate 0.6s;
  }

  @media (scripting: enabled) and (prefers-reduced-motion: no-preference) {
    :where([data-in-view="false"]) .c-feature__image {
      opacity: 0;
      translate: 0 1rem;
    }
  }
  ```

- hover の表現は、hover できる環境だけに限る（`@media (hover: hover)`）。タッチ端末では、別の手段で操作できるようにする。

## 9. ブラウザサポート

Baseline の状況は時期によって変わる。判断するときは、その時点の状況を確かめる（modern-web-guidance のガイドに、機能ごとの状況が書いてある）。

この節は、このプロジェクトのブラウザサポートの方針として扱う。modern-web-guidance がフォールバックを勧めていても、この方針で読み替える。

- Baseline Widely available の機能（ネスト、`@layer`、`:has()`、コンテナクエリなど）は、フォールバックなしで使う。ビルド時の変換（PostCSS など）は入れない。
- Newly available の機能は、公開時期と照らして、使うかどうかを個別に判断する（例：相対色構文）。使うと決めたら、理由と時期を設計書に残す。
- フォールバックが要るときは、`@supports` で囲み、対応していないブラウザでは機能を省いても成り立つようにする。HTML や JavaScript の API のポリフィルを入れるかどうかは、プロジェクトで決める。
- `var()` を含む宣言は、読み込み時の構文チェックを通ってしまう。そのため、「同じプロパティを 2 回書く」フォールバックは効かない。フォールバックが必要なら、`@supports` で囲む。

## 10. 作業環境

- スタイルガイドのページを、作業場として置く。
  - トークンの一覧は、CSS のファイルから自動で抽出する。手で書き写すと、実物とずれていくため。
  - 部品の見本は、要素の有無の組み合わせごとに並べる。部品やバリエーションを増やしたら、見本も足す。
- DevTools で、スタイルの出どころを追えるようにする。
  - 開発時は、CSS のソースマップを出す。
  - ビルドで、CSS を HTML にインライン化しない。
- 書式（字下げ、改行、空白）は、プロジェクトの決まりに従う。
  - プロジェクトにすでに書式の決まり（`.editorconfig`、Prettier や Biome などの整形の道具とその設定）があれば、そちらに従い、この Skill の既定値で置き換えない。
  - 決まりがないときだけ、次の既定値を使う。どのエディターで整形しても同じ結果になるようにするため。
    - プロジェクトに `.editorconfig`（`assets/.editorconfig`）を置く。字下げはスペース 2 つ、改行は LF、ファイルの最後に改行を 1 つ。
      多くのエディターがそのまま読み、エディター全体の設定（タブで字下げする、など）より優先する。
    - CSS の整形は Prettier で行う。Prettier を devDependencies に入れ、設定（`assets/.prettierrc.json`）をプロジェクトに置く。
      エディターの整形は、プロジェクトに入っている Prettier とその設定を使うので、エディターが違っても結果がそろう。
      1 行の長さの上限は 120 にする。標準の 80 では、行末に注釈がある宣言が `var(` の所で割れて読みにくくなるため。
    - `npm run format`（整える）と `npm run format:check`（整っているかを確かめる）を用意し、`format:check` を CI で行う。
    - 途中から入れるときは、整形だけのコミットを分ける。見た目が変わらないことを確かめる。
  - どちらの場合も、書式は Stylelint では検査しない。Stylelint は 16 から書式のルールをなくしたので、Stylelint は 1 節の方針の検査に専念させる。

## 好み

作者の流儀。ほかの人やプロジェクトで使うときは、この節を書き換える。

- クラス名の接頭辞を、レイヤー名に対応させる（`.l-` = layout、`.c-` = components、`.u-` = utilities）。クラス名を見れば、どのレイヤーに属し、何に勝つかが分かる。
- Tailwind などの、ユーティリティファーストのフレームワークは使わない。
- CSS のファイルは少なく保つ。1 レイヤー 1 ファイルでも、`global.css` 1 つでもよい。分け方は、作業しながら変える。`@import` の並び順が、そのまま記述順になる。
- ネストした指定は、結合子で始まるときも `&` を書く（`& > :first-child`、`& > *`）。省略しても意味と詳細度は変わらないが、親のどこにつながるかを、見た目ではっきりさせるため。`&` 以外で省略しても意味が変わらないもの（`*:first-child` の `*` など）は、省略してよい。
- `--font-size-sm` のような、「派生値に名前を付けただけのトークン」は作らない。
- トークンに、サイト固有の接頭辞（`--xx-`）を付けない。`calc()` や `var()` を多用するので、入力の手間を優先する。
- 見た目は、あとで人がブラウザ上で詰める前提。AI が書くスタイルは仮のものとして、シンプルに、あとから編集しやすく書く。
- どのレイヤーに置くか、トークンにするかで迷ったら、決めずに相談する。

## プロジェクトごとに決めること

この Skill では決めない。プロジェクトの設計書に書く。

- トークンの具体的な値（色、書体、余白の基準値など）
- ブレークポイントの値と、その書き方
- 個々の部品の設計
- フレームワークの設定の細部

## assets（ひな形）

新しいプロジェクトで、スタイルの土台を作るときにコピーして使う。値はすべて仮。

| ファイル               | 内容                                                                              |
| ---------------------- | --------------------------------------------------------------------------------- |
| `stylelint.config.mjs` | 1 節のルールの検査。Stylelint 18 以上と `stylelint-config-standard` 41 以上が必要 |
| `global.css`           | レイヤーの順序の宣言と `@import`                                                  |
| `tokens.css`           | トークンの骨組み                                                                  |
| `layout.css`           | layout の基本部品（stack / cluster / grid / split / switcher）の実装例            |
| `.editorconfig`        | 書式の決まりがないときの既定値（10 節）                                           |
| `.prettierrc.json`     | 書式の決まりがないときの Prettier の設定（10 節）。Prettier 3 以上が必要          |

## 書き終えたら確認すること

- 詳細度が [0,1,0]（その要素自身の状態を重ねた場合と、先頭の打ち消しは [0,2,0]。疑似要素の分は数えない）を超えていないか。状態を 2 つ以上重ねたとき、2 つ目からを `:where()` に入れたか。
- 同じ条件を、対象ごとに書き並べていないか（`:where(条件) :is(.a, .b)` にまとめる）。`:is()` の中が、すべてクラス 1 つか。
- block や layout のクラスに、`margin`（`auto` 以外）や、ほかの置かれ方（`align-self`、`flex` など）を書いていないか。
- block に、自分の大きさを固定の値で書いていないか（中身に比例する値、下限、並びの外に出る部品、飾りを除く）。文章の行の長さを、block の側で縛っていないか。
- layout の名前で、中身のことを言っていないか。layout に切り出したのは、同じ並べ方が違う中身で出てきたからか。
- `reset` / `base` で、素の要素に `margin` を付けていないか。
- 文脈の余白を、後ろ側に付けていないか。先頭の打ち消しを、`:where()` に入れずに `> :first-child` で書いたか（`.c-prose` の入れ物の中を除く）。
- `.c-prose` と `.c-prose-end` を、components の先頭に置いたか。`.c-prose` 自身に、継承されるプロパティを書いていないか。
- 1 つの入れ物の中で、`gap` と子の `margin` を混ぜていないか。
- 部品に基準色や色の値を直接書いていないか。派生色で、明るさの向きを決め打ちしていないか。
- 派生値をトークンにしていないか。トークンの名前で、値を置くプロパティを決めていないか（`--page-padding`）。
- 物理プロパティを、意図なく使っていないか。
- 状態をクラスで持っていないか。JS が動かないと見えなくなる指定を、`scripting` で囲んだか。
- Stylelint が通るか。プロジェクトの整形の道具で整っているか。
